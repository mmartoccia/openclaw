Hi @rlerikse — your problem statement matches something I've been
working on in a fork. The "19 sequential check-ins take ~6 minutes"

pattern this week.

Sharing what I have in case it's useful for this thread:

**Working prototype (shell scripts + docs, runnable today):**

- **Concept doc:** [`docs/octopus-orchestrator/AGENT-TELECONFERENCE.md`](https://github.com/mmartoccia/openclaw/blob/octopus-orchestrator-clean/docs/octopus-orchestrator/AGENT-TELECONFERENCE.md) — scopes the primitive, the visual protocol, and the staged PR shape
- **Bidirectional dial layer:** [`docs/octopus-orchestrator/TELECONFERENCE-DIAL.md`](https://github.com/mmartoccia/openclaw/blob/octopus-orchestrator-clean/docs/octopus-orchestrator/TELECONFERENCE-DIAL.md) — file-based handoff primitive so agents can initiate meetings with agents running in different processes
- **Prototype scripts:** [`scripts/teleconference/meet-dial.sh`](https://github.com/mmartoccia/openclaw/blob/octopus-orchestrator-clean/scripts/teleconference/meet-dial.sh), [`meet-check.sh`](https://github.com/mmartoccia/openclaw/blob/octopus-orchestrator-clean/scripts/teleconference/meet-check.sh)

**The key observation that made it tractable:** `openclaw agent --to <chat> --deliver`
already posts _both_ the injected prompt and the agent's reply back to
the channel. So a visible two-sided conversation between two agents is
achievable today as **one CLI call per turn**, no new transport layer,
no plugin wiring. Session history is already persisted per `chat_id` so
multi-turn meetings accumulate naturally.

The PR shape we're converging on wraps that pattern into explicit
verbs (`teleconference dial / pickup / send / wrap`) with a JSON file
per meeting in `~/.openclaw/meetings/{pending,active,closed}/`.
Directories encode lifecycle state via atomic file moves, so no locks
and any session can pick up pending work.

**Evidence it works:** we used the pattern (over the actual telegram
DM bridge to another openclaw agent session) to diagnose and fix a real
bug in the `openclaw octo doctor` feature-flag check — that's commit
[`fb24c1f3d7`](https://github.com/mmartoccia/openclaw/commit/fb24c1f3d7)
in the fork. Two-turn meeting, root cause identified, fix shipped. It
wasn't a toy.

**Where this overlaps with your proposal:**

- ✅ New session type with multi-participant enrollment — same idea,
  we model it as `session.kind = "meeting"` alongside `direct`/`group`
- ✅ Shared message visibility — achieved for free by `--deliver`
- ✅ Moderator-controlled turn order — currently the initiator is
  moderator by default; open design question whether we want explicit
  turn tokens
- ✅ Temporary lifecycle — `pending → active → closed` via directory
  moves
- ✅ Agents return to individual sessions on conclusion — inherent
  because the meeting file is scoped, not the session

**Where we diverge / where I'd love your read:**

- **Where does it live?** Your issue reads like this should be a
  first-party session-store concept. My current sketch puts it one
  layer up in `~/.openclaw/meetings/` so it can cross process
  boundaries (think: Claude Code CLI talking to a running gateway
  agent). Do you see a reason it needs to be inside the session store
  to work?
- **How are participants enrolled?** Your spec describes coordinator
  invitations. Mine starts 1:1 and defers multi-party fan-out to a
  later phase. Should the MVP handle ≥3 participants, or is 1:1 enough
  to learn from first?
- **Turn taking mode** — structured vs. open-floor. I defaulted to
  open-floor (whoever has the turn sends, via whatever channel plugin
  delivers reliably). Yours leaves it configurable. Curious whether
  you had a specific structured mode in mind.

Happy to iterate on this with you — if this is close to what you want,

first PR to wrap the primitive into real TypeScript verbs. If it isn't
close, I want to understand why so I don't upstream the wrong shape.
