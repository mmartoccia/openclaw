This overlaps almost exactly with what I've been prototyping this
week, with one interesting extension. Sharing in case it's useful.

**What you described:**

- `/delegate marketing-agent "Draft 3 tweet variations"` — command
  form
- `agents.send(agentId: "marketing-agent", task: "...", waitForResult: true)` —
  programmatic form
- Agents retain their own workspace, memory, and identity files
- Scoped to "thread-bound agents within the same Gateway instance"

**What I built:**

- `openclaw agent --to <chat-id> --channel telegram --deliver --message "..."`
  as the base primitive — this already works today, no new code. It
  injects the message as user input to whatever agent routes to that
  chat, runs one turn, and posts both sides back to the channel as a
  visible two-sided conversation.
- A scoped **meeting** wrapper that gives the exchange explicit
  lifecycle (`pending → active → closed`) with a JSON file per meeting
  in `~/.openclaw/meetings/`. Directories encode state via atomic file
  moves.
- A **dial** primitive that lets one agent initiate a meeting with
  another and persist the request — so if the receiving agent isn't
  actively running when the dial happens, the request lands in
  `pending/` and the next-running instance of that agent picks it up.

**Concept docs + runnable shell prototype:**

- [`AGENT-TELECONFERENCE.md`](https://github.com/mmartoccia/openclaw/blob/octopus-orchestrator-clean/docs/octopus-orchestrator/AGENT-TELECONFERENCE.md)
- [`TELECONFERENCE-DIAL.md`](https://github.com/mmartoccia/openclaw/blob/octopus-orchestrator-clean/docs/octopus-orchestrator/TELECONFERENCE-DIAL.md)

**The extension your proposal doesn't have but I think it wants:**

Your scope is "same Gateway instance." That's the easy case. The hard
case I hit immediately is **"what if the two agents are in different
processes on the same host?"** — specifically, one is a long-running
gateway-hosted agent, the other is a Claude Code CLI REPL in a
terminal. There's no shared in-memory transport between them.

The file-inbox approach solves this: any process that can write to
`~/.openclaw/meetings/pending/` can dial any agent, and any process
that can read from there can pick up. Same-gateway is the fastest
path (skip the filesystem, go in-memory), but cross-process falls out
for free.

I think the right layering is:

1. **Transport layer** — same-gateway fast path, cross-process
   file-inbox slow path, same API surface. Callers don't need to
   know.
2. **Lifecycle layer** — meeting concept (what this comment is about)
   layered on top of either transport.
3. **API surface** — `openclaw agent teleconference dial / pickup /
send / wrap` as the top-level verb, with `agents.send(agentId,
task)` (your proposed shape) as a shortcut for the simple
   fire-and-forget case.

Would you be open to folding your proposal into a broader RFC that
covers both the same-gateway and cross-process cases? I'd like to file
one that cross-references your issue as the in-process transport
case. If you'd rather keep yours scoped to same-gateway, I'll
reference it as the "fast path" for callers who know they're
in-process and don't need the file-inbox overhead.

**Evidence this works end-to-end:** used the pattern to diagnose
and fix a real `openclaw octo doctor` bug — [commit `fb24c1f3d7`](https://github.com/mmartoccia/openclaw/commit/fb24c1f3d7).
Two-turn meeting between two live agents, root cause found, fix
shipped. Not synthetic.
