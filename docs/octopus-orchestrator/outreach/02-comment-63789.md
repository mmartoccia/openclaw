Strongly aligned with the minimalist framing here. "The smallest
first-party protocol that makes multi-agent delegation reliable enough
to reason about and verify" is exactly where I think the space should
land, and the tradeoffs you've deliberately excluded (workflow engine,
retries, dashboards, DB-backed orchestration) match the ones I'd
exclude too.

Sharing a working prototype that might serve as a concrete
implementation path for the handoff contract you're sketching.

**What I've built in a fork over the last day:**

- **Primitive:** wrap `openclaw agent --to <chat> --deliver` — which
  already posts both the injected prompt and the agent's reply to the
  channel as a visible two-sided conversation — into a named verb
  with explicit lifecycle
- **Lifecycle:** file-system-as-source-of-truth at
  `~/.openclaw/meetings/{pending,active,closed}/<meeting_id>.json`.
  Status transitions are atomic file moves, no locks, any session can
  pick up pending work, lifecycle is queryable via `ls`
- **Handoff acknowledgment:** each file carries `meeting_id`,
  `from_agent`, `from_channel`, `from_chat_id`, `to_agent`, `topic`,
  `reply_via`, `created_at`, `status`, and (on pickup) `started_at` +
  `picked_up_by`. Terminal state adds `ended_at` + `outcome`. That
  closely matches your "delivered/accepted/queued/rejected" shape,
  just with the state encoded as the containing directory rather
  than as a field — which gives us single-writer atomicity without a
  DB or a lock.
- **Append-only ledger:** the `closed/` directory _is_ the ledger.
  No entries are deleted; lifecycle is a forward-only trajectory.
  `meet-check.sh --state all` is the read interface.

**Where I'd love your input on the contract boundary:**

Your Phase 1 scope (`handoff_id`, structured acknowledgment,
control-only result visibility, append-only ledger) maps almost
cleanly onto what the prototype produces. The main design question
I'd ask you is:

> Should the handoff protocol be **aware of the lifecycle** (knows
> about pending → active → closed, can query pending handoffs), or
> should it be **transport-only** (delivery ack + visibility, with
> lifecycle living one layer up in a meeting/session concept)?

I've been treating them as two layers — a transport primitive (your
proposal) and a lifecycle primitive (the meeting concept from #51642).
But there's a plausible reading where they're the same layer and
meetings are just `handoffs.pending`.

If you're open to it, I'd like to:

1. **Align on the boundary** — whatever you decide, I can rework the
   prototype to sit cleanly above/below/inside your handoff contract
2. **Provide the concrete implementation** — the shell prototype is
   throwaway; the real landing would be `src/cli/program/subclis/agent-teleconference.ts`
   with ~800-1200 LOC of TypeScript + tests, composing with whatever
   `handoff_id` + acknowledgment shape your PR settles on
3. **Share the field-tested shape** — the `{pending,active,closed}`
   directory pattern, the `reply_via` field for cross-channel pickup,
   the move-don't-edit discipline — these are all things that came
   out of actually using the prototype and hitting corner cases

No interest in stepping on your PR. I'd rather converge on one path
than fork the conversation. If the alignment is workable I'll file an
RFC that explicitly depends on this PR landing first, with the meeting
verbs as the next layer up. If the alignment doesn't work, I'd still
rather your proposal land alone than try to push two competing
protocols.
