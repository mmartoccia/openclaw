# Comment on #50073 — Skill-based task routing for multi-agent setups

**Target:** https://github.com/openclaw/openclaw/issues/50073
**Tone:** technical, composability-framed, offer to layer
**Why:** Octo's ELO is a natural performance-feedback extension of
their capability-based routing

---

Hi @Hollychou924 — interesting proposal, and I think it composes
cleanly with a different approach being built in [#64392](https://github.com/openclaw/openclaw/pull/64392)
(Octopus Orchestrator, tracking issue [#64435](https://github.com/openclaw/openclaw/issues/64435)).

Your Phase 1 + Phase 2 design answers one question: **"which agents
CAN do this task?"** — matching by declared capability / loaded skills
/ available tools. That's a necessary filter.

Octo's ELO feature (added to the fork this week) answers the orthogonal
question: **"which agents have been BEST at this kind of task
historically?"** — a rating that updates every time a competitive
mission completes and the verdict picks a winner.

Together:

```
capability_index(task)         → set of eligible agents      ← your proposal
elo_rank(eligible, task_type)  → sorted eligible agents      ← Octo's ELO
router.pick(top_k)             → dispatch to the best match
```

**How Octo's ELO works today:**

- Two SQLite tables: `elo_ratings` (per-runtime rating, games, wins,
  losses, ties, last_updated) and `elo_games` (audit log of every
  recorded outcome, includes the pre/post rating snapshot so future
  tooling can replay history)
- Pairwise Elo (K=32) — for an N-way competitive mission, every pair
  of contestants generates an update based on their verdict-decided
  rank. Ties score 0.5/0.5.
- Automatically triggered when a `competitive` mission completes —
  the verdict arm's output is parsed for either
  `{"ranking": ["claude", "codex", "gemini"]}` or
  `{"final_scores": {"claude": 95, "codex": 80, ...}}` shapes, both
  of which are produced by the default judge-arm prompt templates
- Exposed via `/octo elo` (chat) and `openclaw octo elo list` (CLI)
  for operators to inspect the ranking

Code at `src/octo/head/elo.ts` in [`mmartoccia/openclaw@octopus-orchestrator-clean`](https://github.com/mmartoccia/openclaw/tree/octopus-orchestrator-clean).
~300 LOC including a `parseVerdictForElo` helper that tolerates prose-
wrapped JSON in LLM output.

**What I'd like to explore with you:**

1. **Does your capability index return a ranked list or a set?** If
   it's a set (unsorted), ELO could be the natural second-pass sort
   that turns `{eligible agents}` into `[best historical match, ...]`.
   If it's already ranked by your cost model (you mentioned "routing
   cost" metrics), we need to decide whether ELO refines your ranking
   or replaces it.
2. **How would you like to pass historical outcome data into the
   routing decision?** Your Phase 2 mentions `bus.jsonl` from #50066
   as a place routing _could_ factor in past success rates. Octo's
   ELO table is a much tighter representation of that — one row per
   runtime, constant-time lookup, updated every time a competitive
   mission decides a winner. I could expose a `getRating(runtime,
task_type)` helper your router calls in Phase 2.
3. **Cold-start problem.** Your proposal mentions "routing could
   factor in past success rates" speculatively because the data
   doesn't exist yet. Octo is actively generating that data every
   time a competitive mission runs — so if your router picks Octo's
   ELO as its history backend, the cold-start problem solves itself
   naturally as missions accumulate.

**Concrete offer:** once your Phase 1 capability index lands (or
earlier if you want to design together), I can add an `elo_rank` helper
function to Octo's head module that your router consumes directly.
That gives you performance feedback without bolting on a separate
rating system, and gives Octo's ELO a real-world application beyond
just `/octo elo` display.

Would love your read on whether the layering makes sense or if you
see a different shape.
