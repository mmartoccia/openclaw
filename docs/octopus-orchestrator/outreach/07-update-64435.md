## What's shipped locally since Apr 10

**1. Five execution strategies** — mission creation now supports
`execution_mode` to control how arms are spawned and evaluated:

- `direct_execute` — single arm, single grip, no evaluation
- `competitive` — N work arms → N judge arms (each reviews the other
  N-1 outputs in a round-robin) → 1 verdict arm aggregates the scores
- `competitive_single_judge` — N work arms → 1 judge arm evaluates all
  N outputs → returns winner + ranking
- `council` — N work arms → 1 synthesizer arm merges all contributions
  into a unified output
- `collaborative` — sequential chain (draft → refine → polish), each
  arm depends on the prior arm's output
- `consensus` — N work arms → 1 validator arm checks for agreement,
  flags `DISAGREEMENT` or `RESOLUTION` as the result

Each strategy is expressed as a DAG transformation over the original
grip. Given 3 arm templates and a grip "write a haiku about octopi",
`competitive` expands it into 7 grips (3 work + 3 judge + 1 verdict)
with auto-spawned dependencies. Code at `src/octo/head/strategies/`.

**2. Phase cascade auto-spawn** — when grip A completes, the node
agent checks whether any downstream grip is now unblocked and spawns
its arm automatically with A's output threaded into the new arm's
prompt via dependency substitution. This is what makes the 5
strategies work end-to-end without a mission-level coordinator
polling for completions.

**3. ELO ranking persistence** — a new `elo_ratings` and `elo_games`
table in the registry schema. When a competitive mission completes,
the verdict output is parsed for a ranking (`{"ranking": ["claude",
"codex", "gemini"]}` or `{"final_scores": {...}}` shapes) and the
result is recorded as a pairwise Elo update (K=32). Runtime ratings
accumulate across missions — over time, operators get a running
picture of which runtime performs best on which kinds of tasks. Not
auto-used for routing yet; that's a deliberate phase boundary.

**4. Distributed arm execution across hosts** — new `RemotePtyTmuxAdapter`
that spawns arms on remote machines via SSH + tmux. Remote nodes are
configured in `openclaw.json` under `octo.remote_nodes`; missions
target a node per runtime via `--target-node claude=mac-mini
--target-node codex=distiller-rpi5`. Remote sentinel polling runs in
the NodeAgent poll loop, SSHes over to read the exit code + output
file, and transitions the local arm row to `completed`/`failed`.
Proven end-to-end with `codex` running on a Raspberry Pi 5 and
`claude` running on the local Mac mini, coordinating through a single
mission.

**5. Auth failure classification** — arms that fail due to CLI auth
expiry (claude `/login` needed, codex `login` flow, gemini OAuth)
used to surface as generic `exit_code_1`. Now `src/octo/head/classify-failure.ts`
pattern-matches the captured output tail and emits
`reason: auth_required` / `rate_limited` / `network_error` /
`cli_not_found` / `out_of_memory` so operators see the real cause in
the event log.

**6. Per-node concurrent arm cap** — memory-constrained remotes (the
RPi5 has 4GB RAM) break down under more than 1-2 concurrent CLI
agents. `max_concurrent_arms` on a remote node entry enforces the
cap at arm spawn time — scheduler throws `policy_denied` if the live
count on that node already hits the cap.

**7. Durable artifact storage** — arm outputs used to live in
`$TMPDIR/octo-sentinels/*.output`, which gets wiped on macOS reboot.
On mission completion the node agent now copies every completed arm's
output to `~/.openclaw/octo/artifacts/<mission>/<grip>-<arm>.txt` and
points `_output_artifact` in the mission metadata at the durable copy.

**8. `/octo` chat surface** — a native slash command (not a plugin —
registered in `src/auto-reply/commands-registry.shared.ts:828` and
dispatched via `src/auto-reply/reply/commands-octo.ts`) that exposes
the orchestration surface from chat channels. Read-only verbs:
`status`, `mission list/show`, `arm list/show`, `grip list/show`,
`elo`, `doctor`. Mutating verbs (`mission abort/pause/resume`,
`arm terminate`) require a `--yes` suffix as an approval gate — the
handler shows a preview with no `--yes` and refuses to execute until
the operator re-issues the command with confirmation. Gated to
`operator.admin` scope on internal channels.

**9. Doctor feature-flag bug fix** — `openclaw octo doctor` was
silently reporting `[OK] feature-flag: octo enabled=false` regardless
of the user's config because `checkFeatureFlag()` was calling
`loadOctoConfig({})` with an empty object literal and getting back
the schema default. First bug found via ad-hoc agent-to-agent
teleconferencing between a Claude Code session and the openclaw main
agent (see the related teleconference RFC at #65403). Fix reads
`openclaw.json` from disk and now surfaces `enabled=false` as `[WARN]`
with a detail line pointing at the config path.

## Architecture snapshot

Mission → grip → arm relationships as a coherent primitive set:

| Primitive   | Role                                                              | State                                                           |
| ----------- | ----------------------------------------------------------------- | --------------------------------------------------------------- |
| **Mission** | DAG of grips with an execution_mode                               | `active → paused → completed / aborted`                         |
| **Grip**    | Individual task unit with deps                                    | `queued → running → completed / failed`                         |
| **Arm**     | Runtime doing the work (claude, codex, gemini, local agent, etc.) | `pending → starting → active → completed / failed / terminated` |
| **Claim**   | Exclusive resource lock                                           | acquire / release                                               |
| **Lease**   | Time-bounded ownership with heartbeat                             | renew / expire                                                  |

Adapters behind a unified `ArmSpec`:

- `pty_tmux` — full local lifecycle via tmux session + sentinel file + `ProcessWatcher` event emitter
- `cli_exec` — child process with deferred exit handler, no tmux needed
- `structured_subagent` — spawn through the existing `sessions_spawn` mechanism
- `structured_acp` — ACP session via the existing acpx harness
- `remote_pty_tmux` — same contract as `pty_tmux` but the tmux session runs on a remote host via SSH

## Related work from other proposals

Reading the broader multi-agent-orchestration landscape in the
upstream repo, several open proposals touch adjacent primitives that
compose naturally with Octo. Adding short cross-links here so readers
can navigate between them:

- **#38522 — Subagent barrier primitive (spawn N, await all).** Their
  single-cohort fan-out/await primitive is what Octo uses as Phase 1
  of any competitive grip spawn. Octo adds the DAG edges so cohorts
  cascade (work → judge → verdict).
- **#45522 — Long-Running Task Orchestration with Real-Time Progress.**
  Conceptual overlap: Octo's mission/grip model implements a DAG of
  long-running tasks with progress observability. Ryce's critique
  there (no structured step state machine, no per-step timeouts with
  retry, no framework-level deviation signals) describes the gaps
  Octo's primitive set fills — per-grip state transitions, `timeout_s`
  per grip, heartbeat-backed leases for deviation detection.
- **#50073 — Skill-based task routing for multi-agent setups.** Their
  capability-based routing ("which agents CAN do this?") composes
  with Octo's ELO ratings ("which agents have been BEST at this kind
  of thing historically?"). Capability is the eligibility filter,
  ELO is the tie-breaker.
- **#10010 — Agent Teams - Parallel Agent Coordination.** Cooperative
  paradigm that complements Octo's competitive modes. Octo's `council`
  and `collaborative` execution modes cover similar cooperative
  use cases (shared output synthesis, sequential refinement chains).
- **#35203 — Multi-Agent Collaboration Enhancement (Capability
  Profiling + Blackboard + Layered Memory + Token Governance).**
  Octo implements concrete Layer 1 (capability profiling via ELO
  games) and the beginnings of Layer 2 (mission artifacts in
  `~/.openclaw/octo/artifacts/` are a tiny blackboard). The full
  four-layer vision is a natural continuation.
- **#65403 — Agent Teleconference RFC.** Orthogonal coordination
  primitive (scoped meetings between agents) that composes with Octo
  — meetings can produce mission specs, mission outcomes can trigger
  follow-up meetings.
