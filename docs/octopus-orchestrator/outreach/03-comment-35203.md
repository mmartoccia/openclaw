# Comment on #35203 — RFC: Multi-Agent Collaboration Enhancement (Capability Profiling + Blackboard + Layered Memory + Token Governance)

**Target:** https://github.com/openclaw/openclaw/issues/35203
**Author of issue:** (check before posting)
**Tone:** respectful of the bigger vision, position our primitive as a
minimum-viable on-ramp, acknowledge the architectural reach
**Why third:** this is the most ambitious RFC in the space; posting
here is about showing we've read the full landscape, not just the
closest prior art. Positions our work as complementary to theirs.

---

Read this RFC end-to-end — the four-layer framing (capability
profiling → shared blackboard → layered memory → token governance)
is the most structurally honest proposal I've seen in this space.
Every multi-agent system I've built has eventually needed all four
of those, and having them enumerated with academic grounding
(Federation of Agents, MasRouter, Multi-Agent Blackboard systems)
gives the conversation a target to navigate toward.

I want to share something that might serve as a minimum-viable
implementation path for the first layer (or two) of your vision.

**What I've been prototyping:** a scoped multi-agent conversation
primitive — "meetings" — that's the smallest thing I can build on top
of existing openclaw primitives (`openclaw agent --to --deliver`,
session persistence per `chat_id`, channel delivery) while still
producing usable coordination.

- **Concept docs:** [`AGENT-TELECONFERENCE.md`](https://github.com/mmartoccia/openclaw/blob/octopus-orchestrator-clean/docs/octopus-orchestrator/AGENT-TELECONFERENCE.md),
  [`TELECONFERENCE-DIAL.md`](https://github.com/mmartoccia/openclaw/blob/octopus-orchestrator-clean/docs/octopus-orchestrator/TELECONFERENCE-DIAL.md)
- **Evidence:** [commit `fb24c1f3d7`](https://github.com/mmartoccia/openclaw/commit/fb24c1f3d7)
  is a real `openclaw octo doctor` bug fix produced via a two-turn
  meeting between two live agents over telegram

**Where I see it fitting into your four layers:**

**Layer 1 (Capability Profiling):** a meeting's closing outcome
becomes a data point for "which agent solved which kind of problem"
reputation. Combined with Octo's ELO ratings for task-dispatch
competitions (which just landed as a separate feature), you get two
orthogonal reputation signals — who _solves_ well vs. who _explains /
decides_ well — and a matchmaker can route new topics to the best
match. The meeting archive at `~/.openclaw/meetings/closed/` is the
substrate that reputation calculations can read from.

**Layer 2 (Shared Blackboard):** meetings _are_ a tiny blackboard.
Transcripts are structured (topic, participants, artifacts, outcome)
and queryable. Agents can read past meetings on related topics before
starting a new one. This is a far less ambitious blackboard than yours
— no pub/sub, no real-time state sharing — but it covers the
"coordination memory" half of what a blackboard is for.

**Layer 3 (Layered Memory):** the meeting corpus is a natural
candidate for layered memory. Private meetings (between two agents
only) → team meetings (a cluster of agents working on a project) →
global meetings (org-wide decisions that affect routing). The
directory layout can encode visibility tiers via subdirectories
(`meetings/private/`, `meetings/team/<id>/`, `meetings/global/`).

**Layer 4 (Token Cost Governance):** each closed meeting file can
carry `usage_tokens` and `usage_cost` fields from the agent turn
metadata. Budget enforcement becomes a filter on meeting creation:
"you can't dial a meeting if you'd exceed today's budget cap".

**What I'm proposing practically:** a staged implementation where
meetings land first as a minimum-viable coordination primitive, and
each subsequent phase layers on one of your four capabilities. Rough
sketch:

- **Phase 0** (today): shell prototype + concept docs, proven via a
  real bug fix
- **Phase 1**: TypeScript verbs `openclaw agent teleconference
dial/pickup/send/wrap`, ~1 week, replaces the shell script with a
  real CLI surface, adds tests, adds a meeting session type
- **Phase 2**: transcript index + search — `openclaw meetings search
"<query>"` — the read interface to past meetings. This is the
  minimum version of your Layer 2 blackboard.
- **Phase 3**: capability profiling — per-agent tallies of meeting
  outcomes, combined with existing ELO ratings, feeding a matchmaker
  that suggests participants for new meetings. This is your Layer 1.
- **Phase 4**: layered memory — visibility tiers, team/private/global
  classification, permission gates on transcript access. Your Layer 3.
- **Phase 5**: token budget integration — aggregation across meetings,
  daily/weekly caps, overrun detection. Your Layer 4.

My reading is that Phases 0-1 are almost free (we have the code), and
each subsequent phase delivers independent value on its own — so the
five-phase roadmap could ship incrementally instead of needing the full
four-layer architecture to land in one PR.

**Honest position:** I don't want to compete with your RFC, I want to
stand on it. If you agree the minimum-viable-meeting primitive is a
plausible on-ramp to Layer 1/2, I'd like to file a scoped RFC issue
for Phase 1 that explicitly depends on yours staying as the direction
for Phases 3-5. That gives you an implementation beachhead and gives
me a primitive that composes with the bigger vision instead of ending
up orthogonal to it.

The alternative is that my Phase 1 lands as a standalone primitive
that gets used by something that isn't your RFC, and that'd be a
worse outcome for everyone.

**Specific asks:**

1. Does the phasing make sense to you, or do you see a fundamental
   mismatch between meeting-as-primitive and blackboard-as-primitive
   that'd make them incompatible?
2. Your RFC mentions "ambiguous task boundaries" as a problem. I read
   that as "agents don't know when to delegate vs. do-it-yourself." A
   meeting-dial gesture is exactly that delegation decision made
   explicit. Does that framing hold for you?
3. Is there a specific Layer-1 data point you'd want the meeting
   archive to start capturing _right now_ so the future matchmaker has
   good history to train on? Easy to add fields to the meeting JSON
   before the format stabilizes.
