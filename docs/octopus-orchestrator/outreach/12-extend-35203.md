## Your four layers, mapped to what's shipped

### Layer 1 — Capability Profiling

**Your scope:** per-agent capability tracking, performance records,
match-making for task dispatch.

**What's shipped in Octo:** `src/octo/head/elo.ts` — a competitive
rating system that generates Layer 1 data **as a by-product of
running missions** rather than requiring explicit profiling
campaigns. Every time a `competitive` mission completes, the verdict
arm's output is parsed for a ranking and a pairwise Elo update
(K=32) is applied to every participant. Over time the `elo_ratings`
table converges on "runtime X has been the winner Y% of the time on
tasks of type Z" without anyone having to run a dedicated benchmark.

Combined with #50073's capability-index (which I just commented on):

```
capability_index → "who CAN do this?"              ← #50073
elo_rank         → "who has been BEST at this?"    ← Octo
```

Together these two would deliver a minimum-viable Layer 1 that
learns from production usage rather than requiring synthetic
evaluation runs.

### Layer 2 — Shared Blackboard

**Your scope:** shared state for agent discovery, intermediate
results, decisions published to peers.

**What's partially shipped in Octo:** mission artifacts at
`~/.openclaw/octo/artifacts/<mission>/<grip>-<arm>.txt`. Each grip's
output is persisted durably, the `_output_artifact` metadata field
on the mission points at the verdict's output, and the artifact tree
grows monotonically as missions complete.

This is a tiny read-only blackboard — agents can read prior
mission artifacts but don't broadcast active work. For a full Layer
2 we'd need:

- Active state broadcast (pub/sub on in-progress mission state)
- Searchable transcript index over closed missions
- Agent-side hooks to query the blackboard as part of their normal
  tool loop

**What's adjacent:** the teleconference work at [#65403](https://github.com/openclaw/openclaw/issues/65403)
produces meeting artifacts at `~/.openclaw/meetings/closed/<id>.json`.
Together, Octo's mission artifacts + meetings' meeting artifacts form
the substrate of what a fully-built Layer 2 would query. Missing is
the search / query / pub-sub layer on top.

### Layer 3 — Layered Memory

**Your scope:** private / team / global visibility tiers.

**What's shipped in Octo:** nothing yet. This is Phase 4 on the
meetings roadmap (teleconference RFC [#65403](https://github.com/openclaw/openclaw/issues/65403)
scopes this explicitly as deferred). The natural encoding is
subdirectory-as-visibility in the existing artifact trees:
`meetings/private/`, `meetings/team/<id>/`, `meetings/global/` —
permission gates enforced by whoever reads the directory.

### Layer 4 — Token Cost Governance

**Your scope:** per-agent and per-task budgets, overrun detection,
governance.

**What's shipped in Octo:** nothing yet — but the data is already
captured. Every arm turn records `usage.input_tokens`,
`usage.output_tokens`, `usage.total_tokens` in the event log
(from the existing `agent-via-gateway.ts` runtime metadata). Adding
budget aggregation on top is a read-side concern: sum tokens per
mission / per agent / per day, enforce caps at mission-create time.
Probably 150-300 LOC of new code, not a new primitive.

## Staging proposal

If you're open to it, here's how I'd map your four-layer vision onto
concrete work over the next few months:

| Phase                       | Contents                                                                                                                           | Status                                                                                |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| **0 — Primitive substrate** | Mission / grip / arm / claim / lease; 5 execution strategies; phase cascade; distributed arm execution                             | ✅ Done in fork, upstream PR #64392 landing the base                                  |
| **1 — Minimum Layer 1**     | Octo ELO (done) + #50073 capability index (in flight) + a routing helper that composes them                                        | ⚠️ ELO done, capability index in review on #50073, router composition not yet written |
| **2 — Minimum Layer 2**     | Transcript/artifact index + search verb over the existing `~/.openclaw/octo/artifacts/` tree; add `openclaw octo search "<query>"` | 🔜 Not started                                                                        |
| **3 — Full Layer 1**        | Matchmaker that auto-routes new mission topics to best eligible agents based on combined capability + ELO                          | 🔜 Not started                                                                        |
| **4 — Layer 3**             | Visibility tiers on mission/meeting artifacts; permission gates                                                                    | 🔜 Not started                                                                        |
| **5 — Layer 4**             | Budget aggregation + overrun detection; daily/weekly caps; per-agent limits                                                        | 🔜 Not started                                                                        |

This is a superset of the teleconference RFC's Phase 2-5. The two
rollouts (Octo missions and Agent Teleconference meetings) share
Layer 2 (shared blackboard) and Layer 4 (budget governance) naturally
because the substrates they produce live in the same place
(`~/.openclaw/octo/` and `~/.openclaw/meetings/` respectively).

## Specific asks

1. **Does this phasing match what you had in mind?** Your RFC proposes
   9 implementation phases (P1–P9); mine collapses them into 6 with
   heavier focus on "ship a minimum-viable version of each layer
   first, then refine." Open to rearranging if you see a better
   sequence.
2. **Shared substrate or parallel tracks?** Octo's ELO + meeting
   artifacts produce data that Layer 2 can query, but I haven't
   built the query layer yet. Are you interested in owning Layer 2
   as a separate concern that reads from both Octo and meetings, or
   would you rather have each subsystem own its own Layer 2 piece?
3. **Token governance ownership.** Layer 4 feels more orthogonal to
   everything else — it's pure bookkeeping on top of usage metadata.
   Would make sense as a standalone RFC that serves both Octo and
   meetings. Interested in picking it up?

Octo's base primitives are landing regardless; the layering questions
are about how Octo's upcoming features compose with your RFC rather
than whether they exist.
