Hi @Ryce — saw your reply here and I think the Octopus Orchestrator
work in PR #64392 + tracking issue #64435 fills exactly the gap you
identified.

You flagged three things that existing openclaw primitives don't
cover:

1. **No structured step state machine** — you noted `streamTo: "parent"`
   handles real-time output but there's no formal per-step lifecycle
2. **No per-step timeouts with retry**
3. **No framework-level deviation signals**

Octo's mission / grip / arm model provides all three as first-class
primitives:

**(1) Structured step state machine.** Every grip moves through an
explicit state machine: `queued → running → completed / failed`. Every
arm (the runtime executing a grip) has its own state machine:
`pending → starting → active → completed / failed / terminated`. The
transitions are validated in code (`src/octo/head/grip-fsm.ts`,
`src/octo/head/arm-fsm.ts`) so invalid transitions throw rather than
silently corrupting state. Transition events are persisted to an
append-only event log, so replay/recovery works deterministically.

**(2) Per-step timeouts with retry.** Grips have a `timeout_s` field
in the spec. Arms inherit a `retry_policy` from the mission default or
a per-grip override. When a grip exceeds its timeout, the node agent
transitions it to `failed` with `reason: timeout_exceeded` and, if
`retry_policy.max_attempts > 0`, auto-spawns a fresh arm for the same
grip with the attempt counter bumped. Retry backoff is configurable
per mission.

**(3) Framework-level deviation signals.** Three independent
mechanisms:

- **Heartbeat leases** — arms hold a time-bounded lease with a
  renewal interval. If an arm crashes or disconnects, its lease
  expires and the scheduler automatically reassigns the grip. No
  polling from the parent required.
- **Sentinel files** — every arm writes its exit code to a sentinel
  file in `~/.openclaw/octo-sentinels/`. The node agent polls the
  sentinel every 1s via ProcessWatcher. If the tmux session
  disappears without writing a sentinel, there's a 3-tick grace
  period before the arm is marked failed — handles fast-exiting
  commands cleanly.
- **Auth / rate-limit / network classification** — `src/octo/head/classify-failure.ts`
  scans captured output for known failure signatures and emits
  `reason: auth_required / rate_limited / network_error /
cli_not_found / out_of_memory` instead of generic `exit_code_1`.
  Operators see _why_ the arm failed, not just that it did.

**Templates like `research→deliver`, `monitor→alert`, `build→deploy`:**
these map to Octo's DAG-of-grips model directly. A mission is a
directed graph of grips where each edge is a dependency. The existing
5 execution strategies already implement common shapes:

- `collaborative` — sequential chain (draft → refine → polish), each
  grip depends on the prior. This is your `research → deliver`
  template.
- `competitive` — N work grips in parallel → N judge grips → 1
  verdict grip. This is a "best of N" pattern applicable to code
  generation, explanation, summarization.
- `council` — N work grips → 1 synthesizer grip that merges the
  outputs.
- `consensus` — N work grips → 1 validator grip that checks agreement
  and flags DISAGREEMENT/RESOLUTION.

Code is at `src/octo/head/strategies/` in [`mmartoccia/openclaw@octopus-orchestrator-clean`](https://github.com/mmartoccia/openclaw/tree/octopus-orchestrator-clean).
PR [#64392](https://github.com/openclaw/openclaw/pull/64392) lands
the base primitive set (mission/grip/arm/claims/leases) — the
strategies and features above are on the fork and will go upstream as
a follow-up PR once the base lands.

**Real-world proof point:** I used the mission/grip/arm primitives
this week to run a local-only `competitive` mission across claude,
codex, and gemini with a haiku-writing task. The 7-grip DAG expanded
correctly, phase cascaded correctly, verdict produced a valid
ranking, ELO table updated, mission completed cleanly, artifact
landed at `~/.openclaw/octo/artifacts/<mission>/verdict-<arm>.txt`.
Total orchestration overhead ~200ms; the actual agent latency
dominated. No polling code in the parent, no fragile timeout loops —
the scheduler + lease system drove the whole thing.

**Specifically for your use case:** if you're looking at "long-running
task with progress feedback" as a first-class feature, the Octo
primitives already cover the structural parts. What's missing (and
where I'd love your input) is:

1. **Progress streaming to the originating channel.** Octo writes
   events to the append-only log but doesn't currently bubble them
   back to the chat channel the mission was launched from. I could
   wire a thin projection so the operator who ran `/octo mission
create` from telegram sees real-time progress updates in the same
   chat.
2. **Per-step template validation.** Octo validates the DAG at
   mission creation time but doesn't have a named-template concept
   yet. `monitor → alert` could be a named strategy alongside the
   existing 5 if that's a pattern worth codifying.

Happy to iterate on either of these with you. If the mission/grip/arm
primitive shape looks close to what you had in mind, the work to
connect it to your progress-streaming use case is small and concrete.
